# 踩坑模板 — Postmortem

> **何时用**: 切 prod / 升级 / 配置变更后,出现"我以为成功但实际未生效"的 bug,且 ≥2 次重试仍未修。
> **不要用**: 单步就能修的小问题,或纯按文档操作后的疑问。
> **配套**: 真实范例见 `../POSTMORTEM-3-false-success.md`

## 命名规范

`../YYYY-MM-DD-bug-<short>.md`,例如 `2026-10-15-bug-fake-success.md`。

---

## 1. 时序事实(强制表格化)

| 时间 | 我/操作的声明 | 实际 user 体验 | 真相 (落定后) |
|---|---|---|---|

**关键**: 表格是"声明 vs 真实"对照,**不是流水账**。只列 ≥ 2 次 fake success 才填多行,1 次成功可不填此表。

## 2. 为什么我 N 次都"自验通过"

| 提交 | 我的验证方式 | 漏了什么 |
|---|---|---|

**根因**: 一句话总结 — "把 X 当 Y"是最常见模式。
最常见 3 类:
- **grep 0 命中 = OK**(SSR HTML 不显示 client-side error)
- **docker logs 干净 = OK**(Core silent fallback 不报)
- **一次 curl 200 = OK**(没 grep error pattern)

## 3. 我没意识到的 N 个事实(reflection)

每个事实写一段,什么事实 + 怎么会误导 + 怎么改:
1. **事实 A** + 误导点 + 修订动作
2. **事实 B** ...
3. **事实 C** ...

## 4. 真正成功是怎么做的 (systematic-debugging)

1. 第一步真正在做的诊断(不是 grep)
2. 第二步
3. 关键修法(批量 + 验证矩阵)

| 模式 | 修法 |
|---|---|
| anti-pattern X | → 正确模式 Y |
| ... | ... |

**验证矩阵**(任何"修完宣布成功"前必走):
- [ ] 直连 PG 跑 page SQL(query 真执行)
- [ ] 真 HTTP GET 5 page(curl + 用户浏览器亲测)
- [ ] 5 pattern grep 同时跑(SQL / Conn / HTML / Render / Cross-DB)
- [ ] 列字段 + 真值对比(psycopg2 / DataTable)
- [ ] `force-recreate` + 等 5s
